# Vendor & stack research (fact-checked, October 2026)

> Produced by parallel research agents with an independent skeptical verification pass (claims checked against primary sources).
> Treat as a snapshot: vendor APIs and pricing change. Each connector milestone re-validates the specifics it depends on.

## Samsung SmartThings

### Summary
SmartThings can be integrated through its cloud REST API (https://api.smartthings.com/v1). The model is location, then room, then device, then component, then capability, then attribute or command. Device data comes from GET /devices?includeStatus=true and GET /devices/{id}/status, and commands go to POST /devices/{id}/commands. Two things have changed and shape the design. First, Personal Access Tokens (PATs) created on or after 30 Dec 2024 expire after 24 hours, so long-term access needs an OAuth-In (API_ONLY) app. The user creates it with the SmartThings CLI (`smartthings apps:create`), gets one token per location, and the token rotates: a 24h access token plus a single-use refresh token that lasts about 29-30 days. Second, Samsung announced on 23 Jun 2026 that free API access ends after Q3 2026. Paid tiers are targeted for October 2026, with a $4.99/month Personal Plan for non-commercial developers, and creating or managing API Access Apps is said to require a paid tier. Today is 2026-10-11, so the user may have to pay; I could not confirm whether billing is actually being enforced yet. Live updates are hard for a LAN-only app. Normal subscriptions push to a webhook that SmartThings can reach (in practice public HTTPS, plus a CONFIRMATION handshake and signature checks). The newer SSE endpoint that Home Assistant uses needs a special 'sse' scope, and third-party apps report 403 errors on it. ControlHome should therefore default to adaptive polling with a bulk call, offer webhooks as an option for users who expose a tunnel, and treat SSE as experimental. Energy data is fairly good on Samsung appliances: washers, ACs and fridges expose powerConsumptionReport (cumulative Wh, a per-window deltaEnergy, and power), while TVs are inconsistent. No .NET SDK is maintained. The public spec is a 655 KB Swagger 2.0 '1.0-PREVIEW' file, so a small hand-written typed client is the best fit.

### Recommendation
Build a self-contained project, ControlHome.Integrations.SmartThings, behind the generic IDeviceIntegrationProvider abstraction. Treat SmartThings as an optional cloud connector that can be switched off cleanly: it may now need a paid Personal Plan.

1) Client and libraries: write a hand-written typed client on IHttpClientFactory with System.Text.Json source generation. It only needs about 15 endpoints: locations, rooms, devices (list, get, status, health, commands), capabilities/{id}/{v} and /presentation, presentation, scenes, scenes/{id}/execute, installedapps/{id}/subscriptions, and optionally history/devices. Keep status payloads as JsonElement or Dictionary trees, because capabilities are dynamic. Use Microsoft.Extensions.Http.Resilience (the .NET 10-aligned 10.x line, Polly v8) for retries and timeouts. Add a custom DelegatingHandler that reads x-ratelimit-limit/remaining/reset. Treat reset values above 1000 as milliseconds and smaller ones as seconds, because the docs conflict. Add per-device and per-principal token buckets from System.Threading.RateLimiting, with defaults of 12/min per device and a conservative bulk-list budget. Do not take a dependency on SmartThingsNet or the other NuGet packages. The Swagger 2.0 spec can optionally be fed to NSwag, but only as a reference for DTOs. For tests, use WireMock.Net with recorded fixtures shaped like Home Assistant's test fixtures (Apache-2.0).

2) Auth, in the setup wizard under Integrations > SmartThings:
(a) Recommended: OAuth-In app. The wizard tells the user to run `npx @smartthings/cli apps:create` (CLI 2.1.x), choose 'OAuth-In App', and enter scopes `r:locations:* r:devices:* x:devices:* r:scenes:* x:scenes:* r:hubs:*`. Optional extras are `w:devices:*` for rename and `x:locations:*` for modes. Skip rules, which are paywalled via OAuth and redundant with ControlHome's own engine. For the redirect URI, default to https://httpbin.org/get, the reliable LAN-only choice. The user pastes the final redirected URL into ControlHome, which parses code and state. As an advanced option, allow ControlHome's own HTTPS callback URL (e.g. https://controlhome.lan/api/integrations/smartthings/callback), since the redirect happens in the browser, but warn that localhost and LAN redirects are reported to fail. The user enters the client id and secret into ControlHome. The backend generates and stores state (CSRF), builds the authorize URL (https://api.smartthings.com/v1/oauth/authorize), and exchanges the code at POST https://api.smartthings.com/v1/oauth/token with Basic auth. Keep both endpoints configurable; HA uses auth-global.api.smartthings.com/oauth/token.
(b) Dev/test only: paste a PAT, with a visible '24h expiry' banner. The link moves to NeedsReauth when the token expires.
Persist one SmartThingsLink row per location: LocationId, InstalledAppId, Scopes, AccessToken, RefreshToken, ExpiresAt, RefreshTokenIssuedAt, Status, and a rowversion. Encrypt the tokens and client secret with ASP.NET Core Data Protection, with keys persisted to SQL Server or a mounted volume.
Refresh with a hosted BackgroundService:
- Refresh when less than 2-4 h remain, and at least every 7 days even when idle, so the 29-30 day refresh token never lapses.
- Keep refreshes single-flight: an in-process SemaphoreSlim keyed by InstalledAppId, plus a DB-level UPDLOCK or rowversion check.
- Write the new access and refresh tokens atomically before releasing the lock.
- On 400 or 401 from the token endpoint, set Status=NeedsReauth and raise a UI notification.
Handle multiple locations as multiple links.

3) Discovery and model mapping:
- Import with GET /v1/locations, /v1/locations/{id}/rooms (cached; the limit is 50/hour) and GET /v1/devices?locationId=X&includeStatus=true&includeHealth=true, following _links.next.
- Store external IDs (deviceId, componentId, capabilityId@version) mapped to ControlHome Device, Endpoint and Capability entities. Offer SmartThings rooms as suggestions when mapping devices into the ControlHome floor plan.
- Cache capability definitions (attribute JSON schemas, command argument schemas) and presentations in SQL Server with a multi-day TTL. Use them to render generic controls: enum to select, bounded number to slider, boolean to toggle.
- Maintain a mapping table from common SmartThings capabilities to ControlHome canonical capabilities: switch to OnOff, switchLevel to Level, colorControl and colorTemperature to Color, airConditionerMode, thermostatCoolingSetpoint and airConditionerFanMode to HVAC, temperature/humidity/contact/motion sensors, lock, mediaPlayback/audioVolume/tvChannel to MediaPlayer, washerOperatingState and samsungce.* to ApplianceState, and powerMeter/energyMeter/powerConsumptionReport to Energy. Anything unmapped falls back to a raw-capability widget.
- Hide custom.disabledCapabilities and samsungce.unavailableCapabilities by default, with a per-device 'show anyway' override for the Samsung TV energy case.

4) Commands:
- Send POST /v1/devices/{id}/commands with at most 10 commands, batching related commands for the same device.
- Show the change optimistically as 'pending' in the Vue UI, then confirm by event or hot-poll. Mark the command failed after about 20 s without confirmation.
- Expose SmartThings scenes (GET /v1/scenes?locationId, POST /v1/scenes/{id}/execute) as actions in ControlHome automations.

5) Realtime, in tiers:
Tier 0 (default, works fully on the LAN): an adaptive poller.
- Make one bulk call per location, GET /v1/devices?locationId&includeStatus=true, every 30 s (configurable 15-120 s). That is about 30 calls per 15 min against the observed 1000 per 900 s.
- After a command or a UI 'focus', hot-poll that device's /status every 5 s for 30 s, which stays within 12/min per device.
- Diff against the last snapshot, update the state table, publish domain events to the automation engine, and push to the browser with ASP.NET Core SignalR.
- Show an API-call counter in diagnostics, because paid tiers may meter call volume.
Tier 1 (optional, for users who expose public HTTPS through Cloudflare Tunnel, Tailscale Funnel or ngrok): webhooks.
- Set the app's target URL and implement POST /api/integrations/smartthings/webhook.
- Handle CONFIRMATION by doing a GET on confirmationUrl. Verify the HTTP Signature: RSA-SHA256, key from https://key.smartthings.com/key/{keyId} (cached), plus the Digest and Date-skew checks.
- Handle EVENT and the DELETE lifecycle (purge tokens). Always return 200 quickly and enqueue the work.
- Create CAPABILITY subscriptions per location for the key capabilities, or DEVICE subscriptions (at most 40 per installed app).
- Reduce polling to a 5-minute reconcile.
Tier 2 (experimental, behind a feature flag): if the granted scopes ever include 'sse', use POST /subscriptions with a LOCATIONIDS filter and stream registrationUrl, the way pysmartthings does. Do not count on it.

6) Energy:
- Store powerConsumptionReport windows in an EnergyReading table: DeviceId, ComponentId, WindowStart, WindowEnd, DeltaWh, CumulativeWh, PowerW, with a unique key on (DeviceId, ComponentId, WindowEnd) so polls dedupe.
- Store powerMeter and energyMeter samples on change, and honour the unit field.
- Roll up hourly and daily.
- Consider history/devices for backfill after downtime.
- Also capture samsungce.waterConsumptionReport for washers.

7) Future local paths, as separate connector projects in later phases: a .NET port or Python sidecar of the LocalThings OCF/CoAP-DTLS approach for Samsung appliances, and a Matter controller sidecar (python-matter-server or matter.js) using SmartThings Matter multi-admin for Matter devices. Both reduce dependence on the paid cloud API.

### Gotchas
- Paywall timing: Samsung targeted October 2026 for paid API tiers ($4.99/month Personal Plan) and said creating or managing API Access Apps via the CLI will require a paid tier. As of 2026-10-11 I could not confirm whether billing or new limits are actually enforced, so design the connector to degrade gracefully and to report 402/403-style failures clearly.
- PATs created after 30 Dec 2024 expire in 24h. Use them only for development or testing, never as the production auth path.
- Refresh tokens are single-use and rotate on every refresh. A refresh also invalidates the old access token. Two concurrent refreshes, for example from two app instances or a retry storm, will lock the integration out. Enforce single-flight refresh and persist both new tokens atomically.
- The refresh token dies after about 29-30 days without use. Schedule a keep-alive refresh even when the integration is idle.
- API_ONLY tokens are scoped to one location (LOCATION principal). Multi-location homes need one authorization and token per location, and user-level access isn't available to third parties.
- Redirect URIs: http://localhost and https://localhost redirects are reported to fail ('403 Access forbidden to this app' or 'An unexpected error occurred', June to Sept/Oct 2026). Whether HTTPS is mandatory isn't documented. The proven workaround is redirect=https://httpbin.org/get plus manually pasting the code or URL.
- Rate-limit docs conflict. Getting Started lists 12/min per device for status and commands. Service Integrations lists observed limits of 350/60s for status and 120/60s for commands, and describes x-ratelimit-reset in ms where the troubleshoot page says seconds. Drive throttling from the response headers and keep defaults conservative.
- The rooms API is limited to 50 requests per hour, so cache rooms and never poll them.
- Subscriptions: at most 40 per installed app, at most 40 created per 15 minutes, and 15 per 15 minutes for other subscription calls. Deleting all subscriptions and re-creating them on every startup can hit these limits.
- Webhooks need a target URL SmartThings can reach (in practice public HTTPS with a valid certificate), a CONFIRMATION handshake, HTTP Signature verification and fast 200 responses. Otherwise subscriptions get disabled.
- The SSE /subscriptions endpoint and 'sse' scope used by Home Assistant aren't available to self-created apps; developers report 403. Don't plan around SSE.
- A command returning ACCEPTED only means it was queued. Confirm the actual state change through events or polling.
- Device status is the cloud's cached state. Sending the 'refresh' capability command forces a device re-read, but it costs rate-limit budget, so use it sparingly.
- The docs are inconsistent on the command body field name ('component' in examples vs 'componentId' in the field table). Use 'component', as pysmartthings does.
- Device list pagination uses _links.next, and you can't request a page size above the server max. Limits: 300 devices per location and 10 locations per user.
- powerConsumptionReport values are in Wh (divide by 1000 for kWh). Windows are about 15-30 minutes. Many devices report zeros for energy or power. Some TVs list the capability under custom.disabledCapabilities while still sending real deltaEnergy. HA scales EHS heat-pump power by 1000.
- Token endpoints differ between sources: the docs give api.smartthings.com/v1/oauth/token, while HA uses auth-global.api.smartthings.com/oauth/token and api.smartthings.com/oauth/authorize. Make them configurable.
- The Service Integrations docs carry a 'coming soon' banner, and API Access App registration in the Developer Center Console isn't available yet. The CLI (`apps:create`, OAuth-In App) is the current path.
- The OpenAPI file is Swagger 2.0, '1.0-PREVIEW', about 655 KB. Some generators, such as Kiota, prefer OpenAPI 3.x, and generated code for dynamic capability status is poor. Hand-write the client.
- Every NuGet SmartThings library is stale or archived (most recent 2023).
- On the DELETE lifecycle event (user removed the integration in the SmartThings app), delete the stored tokens and data.
- Matter multi-admin only shares Matter devices that are onboarded in SmartThings. SmartThings hubs reportedly do not bridge Zigbee or Z-Wave devices to other Matter controllers.

### Verification: corrections and missed points
- Billing was still not enforced around 2026-10-09/10. In the official announcement thread, users report SmartThings has not started charging, that Samsung has not said how to pay, and that HA connections still work. Samsung has published no billing unit (per user, per app or per location), no plan contents or rate limits, and no regional availability or BRL pricing. Brazil availability is unverified; my web-search budget ran out before I could check Portuguese-language sources. Design for both cases, and add a 'plan required' state that is set by observed error responses, not assumed (https://community.smartthings.com/t/a-new-enhanced-smartthings-api-experience/309947).
- The plan is for 'non-commercial, individual developers', and a community expert notes that owning an API Access app makes you such a developer. ControlHome must never ship or host a shared client_id/secret, which would turn the project into a commercial or partner integration. Each household creates its own app under its own Samsung account. That keeps billing with the user and should be stated in the setup wizard (blog post; thread 311351).
- The new Service Integrations docs list 'A web server with a publicly accessible HTTPS URL' as a prerequisite for API Access Apps. They require Redirect URIs and a Target URL at registration, and the target URL must pass CONFIRMATION before webhooks are delivered. The researcher's 'HTTPS not documented' framing understates this (https://developer.smartthings.com/docs/service-integrations/app-setup).
- A LAN-only install never receives the DELETE lifecycle event. When the user removes the integration in the SmartThings app, ControlHome only finds out when a refresh or API call returns 401. Revocation detection must rely on 401 or invalid_grant, not on webhooks.
- Subscriptions keep firing even after the access token is invalid (architecture page). The disconnect flow must explicitly DELETE /installedapps/{id}/subscriptions. That call is limited to 15 per 900 s observed, and 15 per 15 min on the Getting Started page.
- Restricted devices are hidden from GET /devices by default and need includeRestricted=true. Status is withheld if the token's access level is insufficient (Swagger). This matters for locks and security devices.
- Many Samsung appliance controls need 'remote control' enabled on the appliance itself, and some features exist only in the SmartThings app (HA docs). The UI should show remoteControlStatus and disable start or stop controls when it is off.
- The Getting Started page also limits 'all other Device APIs' to 12/min, which probably covers the bulk GET /devices list and /health. That conflicts with the 'observed' 1000/900 s figure. Default to polling at 30-60 s and let response headers adjust it. The header unit conflict (seconds vs ms) also appears in the Swagger spec, which says ms.
- Authorize-URL ambiguity: the docs use api.smartthings.com/v1/oauth/authorize, HA uses api.smartthings.com/oauth/authorize, Swagger says auth-global.api.smartthings.com, and an Oct 2026 report says the api.smartthings.com authorize URL returned a load-balancer 403 while account.smartthings.com reached login. Treat all three as configurable and validate them with a real app before the wizard ships.
- Re-authorizing an already-authorized location returns the same (unexpired) token (staff, thread 309234). Each authorized location consumes one of the app's default 500 installations.
- Development of the CLI-based app-creation path is in flux. Console registration is 'coming soon', and creating or managing API Access Apps is announced as paid. Setup-wizard instructions should be data-driven or kept in docs so they can change without a code release.
- The device history endpoint is absent from the public Swagger spec and exists only in the TypeScript SDK. Don't build backfill on it, or keep it behind a feature flag.
- HA's own docs advise users to migrate local Zigbee/Z-Wave devices before October 2026. For ControlHome, hub-attached devices are better served by local controllers (Zigbee2MQTT or ZHA-style over MQTT, Z-Wave JS, a Matter controller) than by the paid cloud API. This should shape the phase plan, not only 'future local paths'.
- LocalThings' HTTPS:8888 path speaks only TLS 1.0, and some devices need a manually imported PSK. My inference, not verified for .NET 10: a native .NET port on Linux would need weakened OpenSSL settings, and CoAP/DTLS with X.509 tooling in .NET is immature. A Python sidecar container running the MIT smartthings-local or LocalThings code is the lower-risk route.
- httpbin.org as the redirect sends the single-use auth code to a third-party server. The risk is low because the code can't be exchanged without the client secret, but the wizard should say so and let the user choose any HTTPS URL they control.
- HA's integration has no handling for 402 or plan-related errors. Nobody knows yet what status code or body the paywall will return, so classify failures defensively: 401 means reauth; 402, and 403 with a plan-related body, mean plan required; 429 means backoff.

### Revised recommendation (after verification)
Keep the overall design: a hand-written typed client in ControlHome.Integrations.SmartThings behind IDeviceIntegrationProvider, OAuth-In per location, adaptive polling by default, optional webhooks, and SSE treated as experimental. Change the following.

(1) Priority and positioning: make SmartThings an optional cloud connector in a later phase, not Phase 1. As of 2026-10-11 the paid Personal Plan ($4.99/mo) has been announced but, per user reports, is not yet enforced, and billing details and Brazil availability are unknown. Build local-first paths alongside it: a Matter controller sidecar, an MQTT/Zigbee2MQTT or Z-Wave JS path for hub devices, and a Python LocalThings/smartthings-local sidecar for Samsung appliances, not a .NET port.

(2) Auth:
- Each household creates its own OAuth-In / API Access app; never ship a shared client.
- Make the authorize and token URLs configurable, defaulting to the documented /v1 URLs, with presets for the HA URLs (api.smartthings.com/oauth/authorize and auth-global.api.smartthings.com/oauth/token). Validate against a real app before release.
- The redirect is any HTTPS URL the user chooses, followed by manual paste of the redirected URL. Present httpbin.org/get as a community workaround and disclose the third-party exposure.
- Refresh single-flight with persisted rotation, plus a keep-alive refresh at least weekly. Map invalid_grant or 401 to NeedsReauth, since a LAN-only install never receives the DELETE lifecycle event.
- Keep PAT mode for development only, with a 24h banner.

(3) Errors: classify 401 as reauth; 402, and 403 with a plan-related body, as 'SmartThings plan required' (a distinct link status and UI banner); 429 as backoff using X-RateLimit headers, where the reset unit is ambiguous (ms per the spec and api-overview, s per the rate-limits and troubleshoot pages); and 422 as a guardrail.

(4) Polling and discovery:
- Bulk-poll GET /v1/devices?locationId=X&includeStatus=true&includeHealth=true&includeRestricted=true every 30-60 s, following _links.next.
- Budget against the conservative '12/min other Device APIs' bucket, and widen only when headers allow.
- Hot-poll a device at most every 5 s for a short window after commands.
- Cache rooms and capabilities.
- Show remoteControlStatus and gate appliance commands on it.

(5) Commands: use the 'component' field (per Swagger), at most 10 commands per request, and treat ACCEPTED as pending until state confirms it.

(6) Webhooks (optional tier): only for users with a public HTTPS target URL (Cloudflare Tunnel, Tailscale Funnel). Handle CONFIRMATION, verify RSA-SHA256 HTTP Signatures with keys fetched from key.smartthings.com by keyId (cached), return 200 quickly, and always DELETE subscriptions on disconnect, because they outlive tokens.

(7) SSE: feature flag only, attempted only if the token's granted scopes include 'sse'. Expect 403.

(8) Energy: store powerConsumptionReport windows deduplicated on (device, component, end) in Wh, honour device-reported units, apply HA's EHS ×1000 quirk, and allow a per-device override for TVs that list the capability under custom.disabledCapabilities. Don't rely on the undocumented history endpoint for backfill.

(9) Setup-wizard instructions for creating the app (CLI vs Developer Center Console) should live in docs or config, because Samsung is changing that path and paywalling it.

## LG (ThinQ Connect + webOS TV)

### Summary
LG needs two separate connectors in ControlHome. (1) LG ThinQ Connect is the official cloud REST API for appliances, authenticated with a Personal Access Token (PAT) created at connect-pat.lgthinq.com. A Brazil account maps to the Americas region, https://api-aic.lgthinq.com. Real-time updates come over outbound-only MQTT to AWS IoT Core: ControlHome registers a client, sends a CSR to get a client certificate, then subscribes to a topic. Because every connection is outbound, this works for a LAN-only Docker app as long as the host has internet access. (2) LG webOS TVs are not part of ThinQ Connect. They are controlled locally over the SSAP WebSocket (wss://TV:3001 on current firmware, ws://TV:3000 on old sets). The user accepts a pairing prompt on the TV, ControlHome stores the client-key it returns, and Wake-on-LAN powers the TV on. The official Python SDK (thinqconnect 1.0.14, Sep 2026, Apache-2.0, used by Home Assistant's LG-maintained lg_thinq integration) is small and readable, so porting its REST and MQTT layers to C# is straightforward. Three risks matter: LG publishes no number for its hourly API-call limit; ThinQ energy data is daily Wh history only, with no live watts; and webOS 26 (2026 firmware) rejects the old signed SSAP pairing manifest. Since webOS 26, clients must pair with an unsigned manifest and may lose elevated permissions such as WRITE_SETTINGS and the pointer/button input socket.

### Recommendation
Build two separate connector projects behind ControlHome's shared IDeviceConnector abstraction: ControlHome.Connectors.LgThinq (cloud) and ControlHome.Connectors.LgWebOs (local). Neither depends on third-party LG NuGet packages: port the official SDK's logic yourself, and write the SSAP client on the built-in ClientWebSocket.

A) LgThinq connector (port of pythinqconnect thinq_api.py and mqtt_client.py, Apache-2.0, credit kept in NOTICE)
1. Setup UI (Integrations > LG ThinQ): link to https://connect-pat.lgthinq.com, the list of scopes to tick, a PAT field and a country picker (default BR). Map the country to a region with the SDK's country table (BR → aic) and use https://api-aic.lgthinq.com.
2. Generate one client ID per installation, e.g. "controlhome-" + Guid, and keep it in SQL. Never create a new one per restart, because creating many clients can get calls blocked. Store the PAT, client private key and certificate encrypted with ASP.NET Core Data Protection, with the key ring on a Docker volume.
3. Check the PAT with GET /devices. Map error codes to UI messages: 1103/1218 invalid token (ask for a new PAT), 1304 terms not accepted, 1306 call limit exceeded, 1307 country not supported, 1309.
4. HTTP layer: a typed HttpClient (IHttpClientFactory) whose DelegatingHandler adds Authorization, x-country, x-client-id, x-api-key (the SDK constant, kept in config), x-service-phase=OP and a new 22-character x-message-id per call. Add Microsoft.Extensions.Http.Resilience for retry and timeout (15 s, matching the SDK), and a System.Threading.RateLimiting token bucket per PAT, conservatively about 1 request per 10 s sustained with small bursts. On 1306, back off for an hour.
5. Discovery: GET /devices, then GET /devices/{id}/profile and GET /devices/energy/{id}/profile. Cache profiles in SQL, refreshing on device changes or weekly. Build capabilities generically from the profile (resource.property, type, read/write mode, enum values, range min/max/step, unit), so every one of the roughly 30 types works out of the box. Add curated UI mappings (power, mode, temperature, run state, remaining time) for AC, washer, dryer, washtower, refrigerator, dishwasher, air purifier, dehumidifier and robot cleaner.
6. Real-time, all outbound:
   - POST /client with allowExist=true.
   - If no certificate is stored: create an RSA-2048 key with System.Security.Cryptography, build a CertificateRequest with CN=lg_thinq signed with SHA-512, send the base64 DER without the PEM header and footer to POST /client/certificate, and save certificatePem, the private key and subscriptions[0]. Retry no more than once a minute.
   - GET /route to read mqttServer.
   - Connect with MQTTnet 5.2.x over TLS on port 8883: client certificate, AmazonRootCA1 bundled in the image, the same client ID, CleanSession=false, keepalive about 30–60 s. Subscribe to the topic at QoS 1.
   - For each device, POST push/{id}/subscribe and event/{id}/subscribe with the SDK's body, treating 1207 as success. Subscribe to push/devices so new or removed devices are noticed.
   - A hosted service re-posts event subscriptions every 24 h, and on every MQTT reconnect. Reconnect with exponential backoff.
   - Message handling: DEVICE_STATUS merges 'report' into the cached state, writes the state history and pushes it to the Vue UI over SignalR. DEVICE_PUSH turns pushCode into a ControlHome notification and an automation trigger.
7. Polling: one GET /state per device at startup and after reconnects. Poll only while MQTT is down, no more often than every 5 minutes per device.
8. Control: POST /devices/{id}/control with x-conditional-control: true and the payload {resource: {property: value}}. Validate against the profile first. Group dependent properties into one call. Show errors 2301–2305 and 1308 clearly, e.g. "Enable Remote Start on the appliance", "Device is off".
9. Energy: a daily job at a random time each morning that fetches DAILY usage for yesterday and MONTHLY usage for the current month, for each energy-profile property. Store it in an EnergyReading table (DeviceId, Property, Period, Date, Wh). Label it in the UI as daily history, not live watts.

B) LgWebOs connector (own SSAP client)
1. Discovery: SSDP M-SEARCH with ST urn:lge-com:service:webos-second-screen:1, plus manual IP entry.
2. Connection: ClientWebSocket to wss://IP:3001 first, falling back to ws://IP:3000. Use a per-host RemoteCertificateValidationCallback that pins the SHA-256 fingerprint on first use and stores it in SQL. Never turn validation off globally.
3. Pairing: send hello, then register with an unsigned manifest (pairingType PROMPT plus the permissions list, as in aiowebostv 0.9.2 or later, which webOS 26 accepts). The UI shows "Accept the prompt on your TV". Store the client-key encrypted. Optionally try the legacy signed manifest first on pre-webOS-26 TVs, falling back on a 403, to keep WRITE_SETTINGS.
4. Runtime: a long-lived connection per TV in a BackgroundService. Ping roughly every 5–10 s. Subscribe to getPowerState, getVolume and audio/getStatus, getForegroundAppInfo, getExternalInputList and getSoundOutput, and push changes over SignalR. Treat a refused or dropped socket as Off/Standby and reconnect with backoff.
5. Commands: power off, volume set/up/down, mute, switch input, launch app, list apps and inputs, channel up/down/open, media play/pause/stop, screen on/off, toast and alert notifications (also usable as an automation action), sound output. Use the pointer input socket for remote buttons when the TV grants it.
6. Power on: after pairing, read the MACs from connectionmanager/getinfo. Send WoL magic packets (3 packets to the subnet broadcast address on UDP port 9). Tell users to enable "Turn on via Wi-Fi" or "Wake on LAN" on the TV and to prefer a wired connection.
7. Docker: run the backend with network_mode: host on the Umbrel/Linux host, which also helps SSDP, mDNS and other LAN vendors. If bridge networking is required, ship a tiny WoL/SSDP relay sidecar on host networking.

Libraries: MQTTnet 5.2.x; Microsoft.Extensions.Http.Resilience (10.x); System.Threading.RateLimiting, System.Net.WebSockets and System.Security.Cryptography (all built in on .NET 10); ASP.NET Core Data Protection; SignalR for UI push. Keep LG-specific code inside the connector projects. Expose devices to the core as generic capabilities (Switch, Thermostat, Mode, Level, RunState, Energy, MediaPlayer) so automations and dashboards work the same way for every vendor.

### Gotchas
- ThinQ Connect is cloud-only. LG appliances need internet access even though ControlHome runs only on the LAN. Every connection is outbound (HTTPS 443 and MQTT/TLS 8883 to AWS IoT), so no port forwarding or tunnel is needed.
- LG publishes no number for the PAT rate limit. It is per user per hour and adjustable by LG, and polling many devices gets you 'Exceeded User API calls' (1306). Rely on MQTT push and keep polling minimal.
- Do not create a new client ID on every start, and do not request a new certificate on every start. Persist both. LG warns that excessive client creation gets calls blocked, and certificate issuance is throttled to about one per minute.
- Use the PAT header set from the official SDK (x-country, x-client-id, x-api-key constant, x-service-phase OP). LG's public docs show a different partner header set (x-country-code, x-service-id, x-service-key) that does not apply to PAT use.
- The country must match the LG account's home region (BR maps to the aic region), not where the user currently lives. A wrong country gives unknown-user or country-not-supported errors.
- PAT expiry is undocumented; one user saw a token fail after about 3 months. ControlHome needs a 'replace token' flow, not only delete and re-add.
- Event subscription expiry: the SDK sends 4464 h while the docs say 1–24 h. Refresh at least every 24 h and on every MQTT reconnect, and treat 1207 ALREADY_SUBSCRIBED as success.
- There is no live power (W) from ThinQ. Energy is historical Wh per day or month, available only up to the previous day. For live consumption, plan smart plugs or a whole-home meter through another connector.
- Legacy LG models only report status about every 5 minutes. Some devices have no push codes (robot cleaner, microwave). MQTT status updates can arrive out of order.
- Remote control of washers, dryers and dishwashers often requires 'Remote Start' to be enabled on the appliance itself; errors 2301–2305 cover remote-off, wrong state, power-off and similar cases. Some devices need several properties in one control call (error 2207 otherwise).
- Washtower and washcombo devices expose sub-devices (washer and dryer) under one deviceId. Home Assistant keys MQTT reports by deviceId plus the first report key for WASHTOWER. Multi-location devices such as refrigerators use locationName.
- LG TVs are not in ThinQ Connect. They need the separate local webOS connector.
- webOS 26 (2026 firmware 43.00.92+) rejects the legacy signed SSAP manifest (403 blacklisted certificate). Clients must use an unsigned manifest, and TVs paired the old way must be paired again. Elevated features such as setSystemSettings/WRITE_SETTINGS (picture mode, backlight) and sometimes the pointer/button socket return 401.
- Current firmware closes ws port 3000; use wss on 3001 with a self-signed or LG-CA certificate and pin it per host. Pre-2018 sets support only 3000.
- The TV cannot be powered on over SSAP. You need Wake-on-LAN, with 'Turn on via Wi-Fi/Wake on LAN' enabled on the TV, the TV's MAC, and the same subnet. Wi-Fi WoL is unreliable on some models and deep standby closes port 3001 about 10 s after power-off.
- In Docker bridge mode, WoL broadcasts and SSDP multicast usually do not reach the LAN. Use host networking or a host-network relay sidecar. Docker Desktop on Windows or Mac cannot do host networking properly, so test WoL/SSDP on the Linux/Umbrel host.
- Pairing requires the TV to be on and the user to accept the on-screen prompt. 'LG Connect Apps' or an equivalent network setting must be enabled.

### Verification: corrections and missed points
- **outdated**: HA's integration is Cloud Push (since 2024.11). Energy sensors give yesterday, this month and last month in Wh, refreshed each morning. Legacy models report every 5 minutes. Robot cleaners and microwaves have no notification codes. → The docs page still reads this way, but HA PR #172983 (merged 2026-06-22) added an energy_today sensor polled hourly. Its PR says the API returns 'per-hour Wh data for the current day (completed hours only)'. PR #182810 (2026-09-21, by LG-ThinQ-Integration) moved the daily poll to a random time between 01:00 and 05:59. So energy is not only previous-day history: intraday Wh with up to 1 h lag is available. There is still no live W. The microwave lists 'none' for notifications; robot-cleaner codes are simply not listed. (https://github.com/home-assistant/core/pull/172983)
- Energy is not daily-only. Since HA PR #172983 (June 2026), the ThinQ API is used for per-hour Wh for the current day (completed hours only, up to 1 h lag), polled hourly at about 24 calls per device per day. ControlHome can show 'energy so far today'. There is still no live watts.
- LG's own integration team (HA PR #182810, Sep 2026) spread the nightly energy poll across a random time between 01:00 and 05:59 to 'mitigate server-side rate limits and thundering herd'. ControlHome's energy job should use the same randomized window and keep hourly 'today' polling optional, or limited to a few devices, given the unpublished hourly cap.
- The official SDK does not persist MQTT credentials. Every startup it re-registers the client (allowExist), generates a new RSA key and CSR, and gets a new certificate; on unload it DELETEs the client registration. Persisting the certificate, as recommended, is untested against LG's backend. Implement 'stored cert → on TLS or auth failure, re-register and re-issue (≤1/min)', and DELETE the client only when the integration is removed.
- The SDK uses MQTT keep_alive_secs=6 and fetches AmazonRootCA1 from amazontrust.com at runtime. AWS says X.509 MQTT sessions last 1–2 weeks at most and can be minutes. Bundle the CA, and design reconnect plus resubscribe as the normal path, not an edge case.
- The ToS position was confirmed by the LG maintainer: the PAT API is 'intended for personal and non-commercial use', and commercial use needs the ThinQ Business API. ControlHome is fine as a self-hosted personal app, but each household must bring its own PAT. Never bundle or share a PAT, and keep the SDK's x-api-key constant configurable in case LG rotates it.
- Since 2025 LG warns that unofficial and reverse-engineered ThinQ clients (the old ThinQ v1/v2 API used by wideq and smartthinq_sensors) 'may change without notice or become unavailable'. Do not use those as a fallback for older appliances; ThinQ Connect is the only supported path.
- Brazil availability is unverified. BR maps to aic in the SDK, but LG publishes no country list, and HA forum reports show 'country is not supported' for some countries until LG fixed it server-side. Run a Phase-0 spike with the owner's real BR account (GET /devices, one control call, MQTT connect) before building the UI.
- Device topology needs care. DEVICE_WASHTOWER is one deviceId with washer and dryer sub-reports, while DEVICE_WASHTOWER_WASHER and DEVICE_WASHTOWER_DRYER are separate deviceIds linked by groupId. Washcombo has MAIN and MINI types. Refrigerators and similar devices use profile 'locations' and locationName sub-devices. The ControlHome model needs parent/child device support.
- HA's lg_thinq has no reauth flow, and users must delete and re-add the integration on PAT failure. ControlHome should support 'replace PAT' in place, keeping the client ID, device IDs, room and floor-plan assignments and automation references.
- webOS 26 pairing is still fragile after the fix (a 'Client key not set, pairing failed' report on HA 2026.8.3, 2026-09-01). aiowebostv also sends a pre-registration GET_SYSTEM_INFO that newer webOS needs, which a C# port must replicate. Upstream rejected a signed-first fallback (issue #728 and PR #729 closed 'not planned'), so treat signed-manifest attempts as unsupported and risky.
- The webOS TLS certificate is a static LG certificate shared across TVs ('LGE TV SSG' from LG's private CA, per lgtv2). Per-host fingerprint pinning cannot distinguish one LG TV from another, so it gives limited assurance. That is acceptable on a LAN, but do not oversell it.
- SSAP is not an officially documented or supported LG API; it is community reverse-engineered. LG can break it with firmware updates, as webOS 26 did. Isolate it behind the connector, version the manifest and permission set, and surface 'TV firmware changed, re-pair' clearly in the UI.
- Dev environment: the user is on Windows 11. Docker Desktop has host networking only from 4.34+ and only at layer 4 (TCP/UDP; no documented broadcast or multicast support), and it requires opting in. Test WoL and SSDP on the Linux/Umbrel host. On Umbrel, the official Home Assistant app already uses network_mode: host plus privileged, so host networking for the ControlHome backend is an accepted pattern there; macvlan is an alternative.
- LG's official Node.js SDK (thinq-connect/jsthinqconnect, Apache-2.0, 27 types, MQTT events) can be used alongside the Python SDK to cross-check the C# port's REST and MQTT behavior and error handling.

A) LgThinq (C# port of pythinqconnect, Apache-2.0, cross-checked against jsthinqconnect)

## Intelbras (cameras/NVR, alarm, Izy/Tuya, access control)

### Summary
"Intelbras" can't be one integration. Its product lines run on at least four unrelated technology stacks, so ControlHome needs one adapter per stack. (1) Izy Smart plugs, switches, lamps and IR devices behave like Tuya white-label (OEM) devices: they show up in the Tuya and Smart Life apps and are advertised as working with Smart Life. Integration therefore means Tuya Cloud OpenAPI plus push events through Tuya's Pulsar message service, with optional LAN control (TCP 6668, protocols 3.3/3.4/3.5) once local keys are pulled from a linked Smart Life account. An Izy app account probably cannot be linked to the Tuya IoT platform directly. (2) VIP IP cameras, MHDX/iMHDX/NVD recorders and most Mibo cameras use the Dahua-style HTTP CGI API with Digest auth (snapshot.cgi, configManager, eventManager attach). Intelbras publishes this API itself (HTTP API V3.35 PDF), the RTSP path is /cam/realmonitor?channel=N&subtype=0|1, and ONVIF Profile S/T is supported. Everything is fully local and is the most mature option. (3) AMT alarm panels use the proprietary ISECNet protocols on TCP 9009: ISECNet v2 on the AMT 8000 family, and ISECNet v1/ISECMobile with 0xE7 framing on the AMT 2018/4010/1016. Several MIT-licensed reverse-engineered implementations (2023–2026) can arm/disarm, read zones and partitions, bypass zones and drive PGMs locally. Real-time events can also come in through 'Receptor IP' mode, where the panel itself connects out to ControlHome. (4) Access-control terminals (SS 3530/3532/3540/5530/5531…) have openly published Dahua-style APIs (accessControl.cgi openDoor, eventManager). Smart locks have no API: Intelbras staff said so in 2020, and the Zigbee locks only work through Tuya/Mibo hubs. The Allo wT7 video doorbell only works through a cloud SDK (Quvii/QVCloud) that has been reverse-engineered, and it can only open doors. There is no single Intelbras developer portal. Camera, recorder and alarm SDKs and protocol documents are handed out through a WhatsApp bot, (48) 2106-0006, which can require a confidentiality agreement, and Intelbras says it does not support third-party apps built on them. Recommended order: Dahua-HTTP/RTSP/ONVIF cameras first (local, low risk), then the AMT panel over ISECNet (local, medium maturity, safety-critical), then Tuya Cloud for Izy, with Tuya LAN control later.

### Recommendation
Model Intelbras as several technology-family adapters rather than one 'Intelbras' integration. Keep the vendor brand as metadata only. Proposed projects (one per family):

1) ControlHome.Integrations.DahuaHttp: Intelbras VIP cameras, MHDX/iMHDX/NVD recorders, Mibo cameras and SS-series access control. Priority: phase 1, local and lowest risk.
- Use HttpClient with SocketsHttpHandler and a CredentialCache set to "Digest". Keep one handler per device, never use Basic auth, and allow a custom HTTP port.
- Identify devices with magicBox.cgi?action=getDeviceType and getSoftwareVersion. Fetch images from snapshot.cgi?channel=N (channel numbering differs, 0 vs 1, so probe it).
- Run one BackgroundService per device that keeps a long-lived GET open on eventManager.cgi?action=attach&codes=[VideoMotion,AlarmLocal,VideoBlind,VideoLoss]&heartbeat=5. Parse the multipart/x-mixed-replace stream, keep the codes list short (firmware truncates it at about 100 chars), and reconnect with exponential backoff.
- Map events onto MotionSensor and other capabilities. For SS terminals, map accessControl.cgi?action=openDoor&channel=1 onto a DoorOpener capability, following the public docs at intelbras-caco-api.intelbras.com.br.
- Use Polly v8 (Microsoft.Extensions.Http.Resilience) with a circuit breaker that never retries 401s quickly, because devices lock out an IP for about 30 minutes after 3–5 bad logins.
- Store RTSP URLs as rtsp://<user>:<password>@host:554/cam/realmonitor?channel=N&subtype=0|1 and hand them to a go2rtc sidecar container (AlexxIT/go2rtc; pin the current 1.9.x release at build time) that restreams RTSP as WebRTC/MSE for the Vue dashboard. Prefer the subtype=1 substream for grids, and prefer H.264 over H.265 for browsers.
- Add a generic ONVIF/RTSP adapter (WS-Discovery plus Profile S/T) as a fallback for other vendors.

2) ControlHome.Integrations.IntelbrasAlarm: AMT 8000/Pro over ISECNet v2, and AMT 2018/4010/1016 over ISECNet v1/ISECMobile. Priority: phase 2, local, safety-critical.
- Write a clean-room C# TcpClient implementation from the MIT references: otavioa/fdaneluzzi homeassistant-amt8000 docs/PROTOCOL.md, Pehesi97, andregoncalvespires, elvis-epx. The v2 frame is dst/src/len/cmd/payload/XOR^0xFF. Auth is 0xF0F0 with 6 digit-bytes (0 encoded as 0x0A). Status is 0x0B4A, arm/disarm is 0x401E, disconnect is 0xF0F1.
- Keep one persistent session per panel, serialised through a SemaphoreSlim, polling every 2–5 s. Expect conflicts with the AMT Mobile/Remoto app.
- Optional real-time path: a 'Receptor IP' TcpListener (e.g. 9010, published from the container) bound to the panel's second IP monitoring destination. It is unauthenticated, so allowlist the panel IP. Don't take a slot the user's monitoring company is using.
- Store the remote-access password with ASP.NET Core Data Protection, require a PIN plus role re-entry in the UI for disarm, and write an audit log.
- Request the official ISECNet docs through Intelbras WhatsApp (48) 2106-0006 ('Obter API/SDK'). Keep any NDA material out of the public repo.

3) ControlHome.Integrations.Tuya: Izy Smart, and any Tuya/Smart Life device from other brands. Priority: phase 3.
- Cloud first. The owner creates a Tuya IoT 'Smart Home' cloud project (data center matching the account region; Brazil accounts are probably Western America/openapi.tuyaus.com, which needs verifying) and re-pairs Izy devices into the Smart Life app, then links that account by QR.
- ControlHome calls the Tuya OpenAPI v1/v2 through HttpClient with HMAC-SHA256 request signing (a small in-house signer; no third-party SDK needed). It uses device list, specification/functions (DP codes such as switch_1, cur_power, cur_voltage, cur_current, add_ele), status and commands.
- Real-time updates come from the Tuya Pulsar message service, using DotPulsar (the official tuya-pulsar-sdk-dotnet uses DotPulsar 3.4.0 on net9.0; check the latest) or the official SDK as reference, over outbound pulsar+ssl :7285. All of this is outbound-only, so it works behind NAT without a tunnel.
- Budget against trial quotas and avoid cloud polling.
- Phase 3b, LAN mode: read local_key and version once from the cloud, then talk to the device directly on TCP 6668. Use your own C# protocol implementation ported from tinytuya (MIT), not TuyaNet (GPL-3.0, only 3.1/3.3). Cover 3.3 (AES-128-ECB), 3.4 (session-key negotiation plus HMAC) and 3.5 (System.Security.Cryptography.AesGcm).
- UDP discovery on 6666/6667/7000 needs Docker network_mode: host, or manual IP entry.
- Fall back to the cloud when the local session fails, and refresh keys after re-pairing.
- Don't reuse Home Assistant's device-sharing client ID.

4) Locks and intercoms.
- No first-party API exists. Expose Zigbee locks (IFR/MFR) as read-only sensors through Tuya Cloud where they appear, with no remote unlock.
- Defer the Allo wT7 because it is a reverse-engineered cloud SDK.
- XPE IP door stations can be handled later through SIP/DTMF or their HTTP config.
- For analog IVR intercoms, recommend a relay (Tuya/Izy switch or similar) on the gate contact.

Cross-cutting design:
- A capability-based device model (Switch, PowerMeter, EnergyMeter, Camera, MotionSensor, ContactSensor, AlarmPanel/Partition/Zone, Pgm, DoorOpener, Lock).
- Every adapter implements IIntegrationProvider and IDeviceDriver as a hosted BackgroundService that publishes state changes through System.Threading.Channels to a state store (SQL Server) and on to Vue via ASP.NET Core SignalR.
- Device secrets are encrypted at rest.
- The containers are the API, the Vue SPA, go2rtc and (external) SQL Server. The API container runs with host networking, or publishes TCP 9010 and the needed UDP ports, for LAN discovery and Receptor IP.

### Gotchas
- Izy Smart is an Intelbras-branded Tuya OEM app, and its account most likely cannot be linked to a Tuya IoT cloud project. Devices usually have to be re-paired into Smart Life, after which the Izy app may stop working for them; the two apps can't be used at the same time. Re-pairing also rotates the Tuya local_key.
- The Tuya IoT Core free trial lasts about a month, then needs manual extension (error 28841002 when expired). It is limited to non-commercial individual use and has monthly API-call and message quotas, so ControlHome must rely on Pulsar push rather than polling.
- Tuya Wi-Fi devices accept only one local TCP connection at a time. Protocol 3.5 needs AES-GCM and 3.4/3.5 need a session-key handshake. BLE-only Izy lamps (EWS 407/409) and Zigbee sub-devices behind ICA 1001/MCA 1001 hubs have no direct LAN key or path, so they are cloud-only.
- UDP broadcast discovery (Tuya 6666/6667/7000) and ONVIF WS-Discovery multicast don't cross a Docker bridge network. Use network_mode: host on the Umbrel box, or offer manual IP entry.
- Dahua-style Intelbras devices use Digest auth and lock out a client IP for about 30 minutes after 3–5 failed logins. Snapshot channel numbering is inconsistent (0 vs 1), eventManager code lists are truncated at about 100 chars, and setConfig can report OK while storing a different value, so read back after writes.
- Recorders allow few concurrent RTSP/playback sessions (1–2 on entry-level DVRs). Browsers can't play RTSP, so a restreamer such as go2rtc is needed. H.265 streams often fail in browsers, so prefer H.264 or the substream.
- Mibo cameras use 'admin' plus the label access key. RTSP/ONVIF use is not homologated by Intelbras, the app may force a key change, and changing the key breaks recorder pairing. Izy-branded cameras (IZC 100x) appear to be Tuya-based and likely cloud-only.
- AMT panels: ISECNet v2 (AMT 8000) and ISECNet v1/0xE7 (AMT 2018/4010/1016) are different protocols. The panel's session can conflict with AMT Mobile/AMT Remoto app use. Polling the remote-access password can flood the panel event log (event 1410). In a shared-password partitioned AMT 4010, disarming one partition can disarm another.
- Receptor IP (push) mode is unencrypted and unauthenticated. Restrict it to the panel's IP and never expose it to the internet. The panel has only 2 IP monitoring destinations, and a monitoring company may already use one.
- Arming and disarming a security system over reverse-engineered protocols is safety-critical. Require re-authentication or a PIN for disarm, keep an audit log, and never make ControlHome the only alarm path.
- Intelbras SDK/API documents for recorders and alarms come through WhatsApp/email and may require a confidentiality agreement (D4sign). Don't commit those files to a public repo, and expect no vendor support (official forum statement).
- There is no API for Intelbras smart locks (staff statement, 2020). IFR 7000 via Tuya exposes status but not lock/unlock. The Allo wT7 relies on a reverse-engineered cloud SDK (Quvii/QVCloud) with no RTSP (port 554 closed), and only door opening works.
- TuyaNet (the main .NET Tuya LAN library) is GPL-3.0 and lacks 3.4/3.5. Linking it would put the project under GPL, so write a port of tinytuya (MIT) instead.
- Reusing Home Assistant's Tuya device-sharing client registration (QR/user-code login) outside HA is a Tuya ToS risk. Use your own IoT-platform project credentials instead.
- Several community integrations are new (2026) and tested on few firmware versions (AMT 8000 FW 3.2.5/3.2.8). Gate features behind detected model/firmware, and add a raw-frame diagnostic mode.

### Revised recommendation (after verification)
Keep the researcher's core architecture. 'Intelbras' is several technology-family adapters, with the brand stored only as metadata, a capability-based device model, hosted BackgroundService drivers, Channels to the state store, SignalR to Vue, and secrets encrypted with Data Protection. Re-prioritize and harden as follows.

Phase 1, ControlHome.Integrations.DahuaHttp (cameras, recorders, SS access control). This is local and low risk, and it is the only family with vendor-published docs (Intelbras HTTP API V3.35, 2023-07-21).
- Use HttpClient with a Digest CredentialCache.
- Add a setup checklist and diagnostics: CGI enabled, Compatibility auth mode, MD5 digest only, and ControlHome's fixed IP on any device allowlist.
- Subscribe with eventManager.cgi?action=attach&codes=[All]&heartbeat=5 and filter locally. Do not hand-tune short code lists.
- Read back after every setConfig.
- Honour the per-device login-failure lock policy and stop retrying immediately on 401/403.
- Use go2rtc v1.9.x (v1.9.14 is current) for RTSP to WebRTC/MSE, preferring the H.264 substream.
- Add an inbound webhook endpoint for the SS 'Event service' push and the XPE 'Ações URL' callbacks, plus an optional syslog listener.
- Map accessControl.cgi?action=openDoor (documented in the HTTP API PDF) and XPE /cgi-bin/ConfigManApp.com?key=F_LOCK&code=… to a DoorOpener capability.
- Add a generic ONVIF/RTSP fallback.

Phase 2, ControlHome.Integrations.IntelbrasAlarm. Treat it as experimental and safety-critical.
- Start by requesting the official ISECNet docs through Intelbras WhatsApp (48) 2106-0006, menu 7 'Obter API/SDK'. The alarm docs reportedly come without an NDA, but keep any vendor material out of the public repo.
- Implement ISECNet v1 for the AMT 2018/4010/1016/1000 Smart in both topologies (ControlHome connects to the panel on 9009, and the panel dials out to ControlHome). Add ISECNet v2 for the AMT 8000 as opt-in, because the community code has very little hardware validation.
- Add a Receptor IP listener on 9010 restricted to the panel's IP.
- Run one serialized session per panel and tolerate AMT Mobile/Remoto session conflicts with backoff.
- Port only from MIT/Apache sources (fdaneluzzi/otavioa PROTOCOL.md, Pehesi97, andregoncalvespires, elvis-epx, thspinto). Do not use caarlos0's custom-licensed code.
- Disarm requires PIN or role re-authentication plus an audit log. Ship arm and monitor only by default, and never present ControlHome as the primary alarm path.

Phase 3, ControlHome.Integrations.Tuya (Izy and any Tuya/Smart Life device). Flip this to LAN-first.
- The free Trial Edition is limited to individual or debugging use, about 26k API calls and 68k messages a month, a maximum of 50 devices and only 10 cloud-controllable devices, with suspension when the allowance runs out.
- Each installation brings its own Tuya IoT project credentials, set up in a setup wizard. Never ship shared keys or reuse HA's device-sharing client ID.
- The user re-pairs Izy devices into Smart Life, accepting that Izy Smart and Smart Life cannot share a device and that re-pairing rotates the local_key, then links the account by QR.
- Make the region selectable (us / us-e / eu …), because Brazil moved to the Eastern America data center for new apps in Nov 2025.
- Use the cloud only for device list, specs, local_key and version, and occasional fallback commands.
- Make an in-house C# port of tinytuya's protocol (MIT) covering 3.1–3.5 (AES-ECB, the 3.4 session key, and AesGcm for 3.5) the primary control and telemetry path, with one TCP session per device and automatic key refetch on decrypt errors. Do not use TuyaNet (GPL).
- Treat Pulsar push as optional, and only after confirming an endpoint exists for the account's data center and that the message volume (energy plugs) fits the quota.
- BLE lamps and Zigbee sub-devices behind hubs remain cloud-only and count against the 10-controllable cap.

Phase 4, locks and intercoms. Zigbee locks (IFR/MFR) get at most read-only state through Tuya cloud, and the IFR 7000 may not work even that way. Defer the Allo wT7, which depends on a reverse-engineered cloud SDK. For gates and analog intercoms, recommend a relay (Izy/Tuya switch) on the contact.

Deployment: run the API container with host networking, or publish TCP 9009, TCP 9010, the webhook and syslog ports, and UDP 6666/6667/7000, to support Tuya discovery, ONVIF WS-Discovery, panel dial-in and device push. Give ControlHome a reserved LAN IP.

Ask the user for exact models and firmware, whether a monitoring company uses the panel's IP destinations, their Smart Life account region, how many Tuya devices they need to control (above 10 rules out cloud control on the free tier), and whether they accept LAN-first Tuya with a one-time cloud key fetch.

## Generic & local protocols (MQTT, Tuya, Matter, Hue, Shelly, cameras)

### Summary
An MQTT core gives the most reach for the least work. It means an MQTTnet 5.2 client in .NET plus a Mosquitto 2.1 container, a native Zigbee2MQTT adapter, and Home Assistant MQTT discovery as a generic intake format. Together that covers Zigbee (Z2M 2.14.x), Tasmota, ESPHome and many DIY devices. Next come Shelly Gen2/3/4 local RPC (simple JSON-RPC over HTTP/WebSocket/MQTT with W/Wh metering) and an optional Home Assistant bridge (REST and WebSocket with a long-lived token), which reaches HA's whole integration catalog. Tuya matters most for Brazil, because Positivo, Ekaza, Multilaser Liv, Nova Digital, Intelbras Izy and Geonav are mostly Tuya OEM products. The Tuya cloud Trial edition is very limited: 26k API calls and 68k messages a month, 50 devices, and only 10 that can be controlled through the API. It also has to be renewed by request, up to 6 months at a time. So the cloud should only be used to list devices and pull local keys, and day-to-day control should run over the Tuya LAN protocol (3.3/3.4/3.5). No maintained .NET library supports 3.4/3.5, so we would port it from tinytuya. Hue (HueApi 3.4.0, CLIP v2 with SSE eventstream) is a small job. Cameras are best handled by a go2rtc sidecar for WebRTC/MSE, with .NET doing ONVIF discovery, PTZ and events. Matter is workable only through the matter.js-based server sidecar (python-matter-server is archived), with host networking and IPv6. Sonoff/eWeLink and Xiaomi miIO are poor value for the effort and should be reached through the HA bridge. The backend container will probably need host networking: mDNS, UDP broadcast and WS-Discovery do not cross Docker bridge networks.

### Recommendation
PRIORITIZED ROADMAP (value vs effort; S = days, M = 1-2 weeks, L = 3+ weeks). This assumes the core platform and the SmartThings/LG/Intelbras adapters are planned separately.

Phase 2, integration framework plus first generic adapters:
1. MQTT core. Value: very high. Effort: M.
   - ControlHome.Integrations.Mqtt uses MQTTnet 5.2.0.1603. One shared IMqttConnection runs as a hosted service with its own reconnect, backoff and resubscribe loop, because v5 has no ManagedClient.
   - Broker: eclipse-mosquitto:2.1 (2.1.2) in docker-compose with listener 1883, allow_anonymous false and the password-file or dynamic-security plugin. Pick Mosquitto over EMQX: it is lighter, EPL/EDL licensed, and avoids the BSL issues and the 6.2.1 single-node bug. Offer "use an existing broker" as a setting. Do not embed MQTTnet.Server, because it ties broker uptime to app restarts.
   - Sub-adapters:
     a. Zigbee2MQTT native. Subscribe to retained bridge/devices, map definition.exposes plus the access bits to the ControlHome capability model, command through <base>/<name>/set, and drive pairing from our UI with bridge/request/permit_join. Ship koenkk/zigbee2mqtt as an optional compose profile; a network coordinator such as SLZB-06 avoids USB passthrough.
     b. Generic HA-MQTT-discovery ingestion. Read both device-based (<prefix>/device/<id>/config with dev/o/cmps) and single-component topics, expand abbreviations and '~', and implement a small Jinja subset for value_template (value_json paths, float/int/round). This covers ESPHome-over-MQTT, OpenMQTTGateway, rtl_433, Z-Wave JS UI and more. Use HA discovery only as an intake and export format, never as our internal schema. Our internal model is a capability model (switch, level, color, colorTemp, powerMeter W, energyMeter kWh, temperature, humidity, contact, motion, lock, cover, thermostat, camera). Later, publish ControlHome virtual devices in the same format so HA can consume them.
     c. Tasmota. Listen for tasmota/discovery/+/config and sensors, and use the cmnd/stat/tele topics plus tele/<t>/SENSOR ENERGY for metering.
2. Shelly Gen2/Gen3/Gen4 local. Value: high. Effort: S-M.
   - Write a small in-house client: one persistent ClientWebSocket per device to ws://ip/rpc, send an initial call with src='controlhome-<id>', then consume NotifyStatus/NotifyEvent. Fall back to HTTP /rpc/Shelly.GetStatus polling.
   - Find devices over mDNS (_shelly._tcp / _http._tcp) using Makaretu.Dns.Multicast.New 0.38.0.
   - Implement SHA-256 digest by hand for WebSocket frames.

   - Realtime: auth, then supported_features with coalesce_messages, then subscribe_events(state_changed) and get_states. Import config/area_registry, device_registry and entity_registry to propose a room mapping, and control through call_service.

### Gotchas
- Docker bridge networking blocks discovery: mDNS (Shelly, Hue, Sonoff, Matter), Tuya UDP 6667/7000, ONVIF WS-Discovery multicast and miIO broadcast. The backend needs network_mode: host or macvlan. Once in host mode it cannot use Docker DNS names, so sidecars must be reached through ports bound to 127.0.0.1. Docker Desktop on Windows behaves differently, so local dev needs manual IP entry.
- Tuya Trial edition: 50 devices max and only 10 controllable via API, 26k calls a month (about 36 per hour, so polling is impossible), 68k messages a month, no overage, and the extension must be re-requested (up to 6 months, not guaranteed). Use the cloud mainly for inventory and local keys.
- Tuya local keys change whenever a device is re-paired or reset. Re-sync keys from the cloud on auth failure. Battery-powered Wi-Fi Tuya sensors sleep and cannot be reached locally. Many devices accept very few simultaneous local TCP sessions, so a parallel tinytuya/LocalTuya/HA connection can fight with ours.
- Tuya DP values are device-specific and scaled. For example, power may be reported in 0.1 W; read the scale from /specifications. One Pulsar consumer per subscription (failover), so dev and prod instances can steal each other's messages.
- Tuya OEM apps (Positivo Casa Inteligente, Geonav Home, Izy Smart, Multilaser Liv, Ekaza) may not link directly to a Tuya IoT Platform project. Devices may need re-pairing into Smart Life/Tuya Smart, which changes their local keys. Unverified.
- Reusing Home Assistant's Tuya device-sharing client registration in ControlHome would amount to impersonating HA and risk ToS problems. Reach that no-developer-account login only through the HA bridge.
- HA MQTT discovery value_template/command_template fields are Jinja2. .NET cannot evaluate them natively, so implement a limited subset and surface unsupported templates instead of failing silently. Retained discovery messages can leave ghost devices; handle empty-payload deletes.
- MQTTnet v5 has no ManagedClient. A naive client never resubscribes after a reconnect, so write the reconnect, backoff and resubscribe loop and test it. MQTT 5 is now the default protocol version.
- Mosquitto 2.x refuses non-local or anonymous connections without explicit config. In 2.1, password_file/acl_file are deprecated (removed in 3.0) and an invalid file on reload makes the broker quit, which can cause a restart loop. max_packet_size now defaults to 2 MB.
- Zigbee2MQTT 2.x removed legacy *_action sensors and renamed some properties (illuminance_lux became illuminance). Map from exposes and the access bits rather than hardcoding property names. Pin the Z2M image version.
- Shelly: Gen1 has a completely different API. On WebSocket you get no notifications until you send a request with a 'src'. aenergy.by_minute is in mWh while total is in Wh. Digest auth is SHA-256 with user 'admin' and realm = device id. There is a limit of 6 simultaneous non-persistent RPC channels. Gen4 devices in Zigbee mode must go through Z2M instead.
- Hue: the bridge cert is signed by the Signify private CA, so validate with bridge-id-as-hostname rather than disabling TLS checks. The eventstream coalesces changes to about 1 per second. Group commands are limited to about 1 per second. The app key needs a physical link-button press within the pairing window.
- Matter: the matterjs-server WebSocket has no auth, so bind it to 127.0.0.1. It needs host networking and IPv6 (Thread routes need IPv6 RA from the border router). Without BLE you can only commission devices already on the network (multi-admin share codes). Its README still labels it Beta and not re-certified by CSA. device_command payloads follow Matter cluster field naming.
- go2rtc: requests from localhost skip auth, and with host networking that includes our backend. Never expose 1984 to the LAN; proxy it through our authenticated backend. WebRTC needs 8555 tcp+udp reachable and candidates set to the LAN IP. Two-way audio needs HTTPS (secure context), which a plain-HTTP LAN app does not provide. Browser H.265 support is spotty, so prefer H.264 substreams.
- Sonoff: non-DIY LAN control needs the devicekey from the eWeLink cloud, and the personal developer tier is OAuth-only with a 1-year credential. From 2026, power, current and voltage no longer update via the cloud, so metering needs LAN. The LAN protocol is reported as unstable.
- Home Assistant bridge: avoid double-control loops when the same device is integrated both natively and through HA, by de-duplicating on manufacturer/serial/MAC. Entity IDs can be renamed, so key on unique_id from the entity registry. The long-lived token gives full admin access to HA, so store it encrypted.
- Xiaomi: accounts are region-isolated, tokens come from the cloud, and the official integration's local mode needs a Xiaomi Central Hub Gateway. There is no .NET miIO library, so the effort is not justified for Brazil.

### Revised recommendation (after verification)
Keep the overall shape: an MQTT core, then Shelly local, then an optional HA bridge, with Tuya, Hue, cameras and Matter in later phases. Apply these corrections:

1) MQTT core
- MQTTnet 5.2.0.1603 with a hand-written reconnect/resubscribe loop, plus Mosquitto 2.1.2.
- On Umbrel, offer "use the existing Umbrel Mosquitto app (mosquitto_broker_1:1883)" and "use the existing Umbrel Zigbee2MQTT 2.14.2 app" as the default path, and bundle our own containers only for non-Umbrel installs.
- Don't enable 'persistence true' together with a persistence plugin.
- Drop the EMQX crash argument. EMQX is a fine single-node choice, but Mosquitto is simpler.
- Map Z2M from exposes and the access bits. Read button events from 'action'.
- HA-discovery intake: support device-based discovery (dev and o are mandatory).
- Tasmota via native discovery only (HA discovery is removed from all builds).
- ESPHome via MQTT only for devices whose configs remove api: or set reboot_timeout: 0s.

2) Shelly Gen2/3/4
- Use WebSocket RPC, sending a request with src before expecting notifications.
- Implement firmware-2.0 digest semantics: base64 nonce, stale=true re-auth, increasing nc, and 429 backoff.
- Keep the 6-channel limit in mind, and store aenergy.total Wh deltas.

3) HA bridge (WS plus REST, long-lived token encrypted)
- This is the pragmatic route to Xiaomi, Sonoff and others.
- Note that HA's Tuya integration is cloud_push, so this bridge does not give local Tuya.
- On Umbrel, HA already runs with host networking, so the bridge is low-friction.

4) Tuya (still the highest value in Brazil, but plan for friction)
- The setup wizard asks for the data center, defaulting to Eastern America (openapi-ueaz) for Brazil with Western America as an option, and derives the matching Pulsar host. Don't hardcode mqe.tuyaus.com.
- Users bring their own Smart Life-linked cloud project. Warn that devices in OEM apps (Positivo, Izy, Geonav, Ekaza) may have to be re-paired into Smart Life before they can be linked, which changes local keys.
- Treat the trial as fragile: 50 devices and 10 controllable, monthly quotas, and no guaranteed extension. Use the cloud for inventory, the DP schema with scale factors, and local_key sync. Use Pulsar for realtime with idempotent handling and a status resync after outages, since messages are kept only about 2 hours.
- Build a clean-room C# port of the local protocol (3.3/3.4/3.5), validated against tinytuya 1.20.0 and real devices. Use the HA bridge or the tinytuya server only as stopgaps.

5) Hue
- Use HueApi 3.4.0 over HTTPS only, validating against the Signify CA with CN = bridge ID, because HTTP is slated for removal.
- Throttle commands conservatively. The 10/s and 1/s figures are unverified heuristics.

6) Cameras
- Run a go2rtc 1.9.14 sidecar with api.listen on 127.0.0.1, plus allow_paths and exec.allow_paths restrictions and local_auth.
- Proxy everything through the authenticated backend.
- Use ONVIF via OnvifDiscovery 3.0.0 and SharpOnvifClient 0.11.2, preferring PullPoint over Basic notifications.
- Plan for HTTPS on the LAN if two-way audio is wanted.

7) Matter
- Run matterjs-server pinned to an X.Y.Z tag with host networking and LISTEN_ADDRESS=127.0.0.1. Use dbus BLE only if needed.
- Default to multi-admin commissioning with network_only.
- If the user already runs Umbrel's Matter Server app (python 8.1.2, same WS API), it can connect for now, but recommend migrating to matterjs-server.
- Avoid MatterDotNet.

8) Sonoff and Xiaomi stay behind the HA bridge. For Xiaomi in particular, the official integration's licence forbids reuse outside HA, the hub is China-only, and there is no South America region.

9) Networking
- Run the backend with network_mode: host on Umbrel, which Umbrel's HA and Matter apps already do. Reach sidecars via 127.0.0.1-bound ports.
- On Windows Docker Desktop, development needs manual IP entry.
- Plan to own the mDNS code (or wrap the stale libraries).

10) Before Phase 3, confirm with the user:
- Which Tuya-OEM brands and apps they use.
- Their app account region (Eastern vs Western America).
- Whether Umbrel already runs HA, Mosquitto, Z2M or Matter Server.
- Whether HTTPS on the LAN is acceptable.

## Stack versions & prior art

### Summary
The fixed stack is mature and current. .NET 10 LTS is at runtime 10.0.12 / SDK 10.0.401 (released 2026-09-08). EF Core 10 supports SQL Server 2025's native json type, complex types mapped to JSON (ComplexProperty(...).ToJson()) and the vector type, and since EF 9 runtime migrations are protected by a database lock, so migrating at startup is acceptable for a single-container appliance. In .NET 10, ASP.NET Core cookie auth returns 401/403 instead of redirects for API endpoints, which suits a same-origin Vue SPA. Identity also gained passkeys, but they only work over HTTPS on a hostname (never a bare LAN IP), so they belong in a later phase. On the frontend, use Vue 3.5.43 (3.6 with Vapor mode is still at RC 11), Vite 8.3.4, Pinia 4, Vue Router 5 and TypeScript 6.0.3. Do not use TypeScript 7, because vue-tsc/Volar cannot run on it until 7.1. The dev machine's Node 20.19.4 runs Vite 8 but not Vitest 5 or the OpenAPI client generators, and Node 20 has been end-of-life since 2026-04-30, so move to Node 24 LTS. Two licensing changes affect library choice. PrimeVue 5 (July 2026) is no longer open source and needs a license key. MediatR 13+ and FluentAssertions 8+ are commercial. That makes shadcn-vue + Reka UI + Tailwind 4, with CSS-variable tokens defined once, the best MIT option for a single source of truth; Vuetify 4 is the batteries-included alternative. SQL Server containers run only on x86-64 hosts and Umbrel's official store requires amd64+arm64 images, so the app image should be multi-arch with the database external or optional. For prior art, borrow Home Assistant's Floor→Area→Device→Entity registry, its trigger/condition/action automations with run modes, and its states plus 5-minute and hourly statistics storage. Also borrow the capability abstraction of openHAB (Things/Channels/Items) and SmartThings (attributes plus commands).

DOMAIN MODEL TO BORROW (prior art)
- Home → Floor (Level int, may be negative; floor-plan geometry and background image) → Room/Area (polygon, icon) → Device (Integration/ConfigEntry owner, Vendor, Manufacturer, Model, Firmware, ExternalIds/Connections such as serial or MAC, ViaDevice hub, Room, Availability) → Entity/Capability.
- Entity/Capability: a stable unique id from the vendor; a typed capability (switch, dimmer, color, powerMeter W, energyMeter kWh, temperature, humidity, contact, motion, lock, thermostat/AC mode+setpoint, mediaPlayer, camera, button/event); attributes with unit, device_class and state_class (measurement/total/total_increasing); supported commands; an optional room override; labels.
- Integrations implement adapters that map vendor capabilities to the canonical model (the openHAB Thing/Channel→Item and SmartThings capability idea) and declare their push/poll strategy.
- Automations: triggers + conditions (AND/OR/NOT, state, numeric, time window, weekday, sun, presence) + actions (device command, scene, delay, wait, notify, if/choose, enable/disable automation), plus run mode, trace history, and Hubitat-style 'required expression' gating.
- Scenes: target-state snapshots. Scripts: reusable action sequences. Blueprints (templates) later.
- History: StateLog (raw, ~10 days) + StatShortTerm (5-minute, ~10 days) + StatHourly (forever; mean/min/max or sum/state/last_reset). This keeps SQL Express well under 50 GB.
- Energy dashboard: per-device and whole-home kWh plus cost from a tariff model (flat, time-of-use such as Brazil's 'tarifa branca', and monthly 'bandeira' surcharge).
- Also plan for: presence, notifications, kiosk/wall-tablet mode, scheduled DB and config backups with restore, audit log, and device offline detection.

### Gotchas
- Node 20.19.4 on the dev machine is EOL (2026-04-30). It satisfies Vite 8's engines, but Vitest 5 requires ^22.12, and @hey-api/openapi-ts and orval require >=22.18. Standardize on Node 24 LTS in .nvmrc, CI and the Docker build stage.
- Do NOT adopt TypeScript 7.x (npm 'latest' is 7.0.2) for the Vue app. vue-tsc and Volar need TS 6 until TS 7.1 ships a stable API, so pin typescript to ~6.0.3. typescript-eslint also only supports <6.1.
- openapi-typescript 7.13 declares peer typescript ^5.x, which causes npm ERESOLVE alongside TS 6. Prefer @hey-api/openapi-ts (TS >=5.5.3 or >=6).
- PrimeVue 5 (since July 2026) is proprietary and needs a PrimeUI license key, renewed yearly even on the free community tier, and shows a banner when verification fails. Do not pick it as the long-term design system.
- MediatR >=13 and AutoMapper >=15 are RPL/commercial and log license warnings. FluentAssertions >=8 is commercial (Xceed). Use plain services or martinothamar Mediator, hand-written or Mapperly mapping, and Shouldly or AwesomeAssertions.
- SQL Server containers run only on x86-64 hosts; ARM/Raspberry Pi Umbrels and emulation are unsupported. Umbrel's official App Store requires amd64+arm64 images, so a bundled SQL Server blocks official-store submission. Keep the database external or optional and make the app image multi-arch.
- The native json type only exists on SQL Server 2025 (compatibility level 170). If umbrel.local runs 2022, EF falls back to nvarchar(max). Calling UseCompatibilityLevel(170) against an older server will break SQL, so detect the version or make it configurable. On first migration EF 10 also converts existing nvarchar JSON columns to json.
- SQL Server Express (the free production edition) has a 50 GB per-database cap, a ~1.4 GB buffer pool, a 4-core limit and no SQL Agent. Telemetry needs rollups and retention like Home Assistant's, and scheduled backups must run from the app, not from Agent jobs. The Developer edition (the container default) is not licensed for production use, so set MSSQL_PID=Express.
- Chiseled .NET images lack ICU and tzdata. SqlClient does not support invariant globalization, and time-zone scheduling (America/Sao_Paulo) needs tzdata, so use aspnet:10.0-noble-chiseled-extra. They also have no shell or curl, so HEALTHCHECK must be exec-form against an app binary or flag.
- Containers run as non-root: UID 1654 'app' by default, while Umbrel prefers 1000:1000. Make sure volume directories (uploads, logs, backups) are writable by whichever UID is chosen.
- Persist ASP.NET Core DataProtection keys to the DB or a volume; otherwise every container restart or upgrade invalidates all auth cookies and protected payloads.
- Passkeys, service workers (PWA install, web push), the clipboard API and crypto.subtle require a secure context. Over plain http://umbrel.local:PORT or a LAN IP they silently fail. WebAuthn RP IDs cannot be IP addresses, and changing the hostname later orphans registered passkeys. Pick the final HTTPS hostname before enabling passkeys.
- MapIdentityApi exposes a public POST /register and issues proprietary, non-JWT bearer tokens. For a setup-first home app, write custom login/logout/me endpoints over SignInManager, or at least block /register after setup.
- .NET 10 cookie auth already returns 401/403 for API endpoints. Do not add custom redirect overrides; let the SPA router handle 401 by navigating to /login.
- ASP.NET Core 10 moved to OpenAPI 3.1 and Microsoft.OpenApi 2.0. Older transformer code samples (OpenApiAny, schema.Nullable) no longer compile, and nullable types are emitted as type arrays, which affects some client generators.
- Quartz.NET 4.x is brand new (4.0 on 2026-09-03, five minors in a month), net10-only and full of breaking changes. Most blog samples are 3.x. Prefer a small custom scheduler (Cronos + SunCalcNet) for automation triggers.
- CoordinateSharp is AGPL/commercial and Innovative.SolarCalculator is LGPL. Use SunCalcNet (MIT) or a self-implemented NOAA algorithm for sunrise and sunset.
- Testcontainers.MsSql's default image is still 2022-CU14 and the parameterless builder is obsolete. Pass the 2025 image explicitly so tests match production json-type behavior.
- SQL Server 2025 RTM images crashed on CPUs or emulators without AVX until CU1. Pin a CU tag (2025-CU9-ubuntu-24.04) rather than RTM, and verify the Umbrel host CPU.
- Vue 3.6 / Vapor mode is still RC (rc.11 on 2026-10-10). Start on 3.5.43 and treat Vapor as an opt-in later optimization; it lacks globalProperties, getCurrentInstance, v-memo and similar features.
- Pinia 4 is ESM-only and needs @vue/devtools-api ^8 installed explicitly. Vue Router 5 moved file-based routing into core, so do not also install unplugin-vue-router.
- If both Umbrel's app_proxy auth and the app's own auth are active, users log in twice. Kiosk tablets and vendor webhooks need PROXY_AUTH_WHITELIST paths, which are then effectively public.
- EF Core named-default-constraint and parameterized-collection translation changes in EF 10 change generated SQL. Review the first migrations and the SQL logs.
- GitHub Action majors moved in 2026 (checkout v7, setup-dotnet v6, setup-node v7 with an ESM/NODE_AUTH_TOKEN behaviour change). Older workflow snippets online use v4 or v5.

## Intelbras follow-up (Twibi presence, gate, intercom, non-AMT sensors)

Almost none of these Intelbras consumer products are Intelbras-native platforms. Each line is a white-label of another ecosystem, so ControlHome should build protocol adapters (Tuya, Zigbee2MQTT/MQTT, Tenda-style goform, TR-069 ACS, Dahua CGI, an HTTP relay trigger, SmartThings cloud) rather than one 'Intelbras' adapter. Evidence: (1) Izy is Tuya. tuya-local ships an Intelbras IFR 7000 profile with Tuya product id a6nttc41, a tuya-local issue shows the IFR 7000 as a Tuya Zigbee sub-device, and HA Brasil users report Izy devices working in the Tuya Smart app. (2) Mibo Smart Zigbee sensors are standard Zigbee 3.0. MSM 1001 is a MultiIR MIR-IR100-E rebrand, supported natively in Zigbee2MQTT 2.11.0. (3) First-gen Twibi Giga+, Fast and Giga are Tenda Nova MW OEM. Their web UI uses a JSON API at /goform/get?module_id=online_list, and there is a working MIT Home Assistant integration tested on Twibi Fast firmware 1.1.10. (4) Twibi Force and the Wi-Force/RX routers run Intelbras' own Linux 'Bifrost' firmware. Intelbras documents TR-069 TR-098 host-table parameters for it (InternetGatewayDevice.LANDevice.{i}.Hosts.Host.{i} with MACAddress, IPAddress, HostName and Active). (5) Intelbras cameras, NVRs and SS-series access controllers are Dahua OEM (Dahua CGI and RPC2 openDoor; supported by rroller/dahua). (6) The XPE 3200 IP intercom family has a documented 'Acionar Relé por HTTP' feature using an Akuvox-style /fcgi/do?action=OpenDoor URL. (7) Consumer Allo intercoms are closed, app-only devices. (8) Matter: no Intelbras vendor appears in the CSA DCL vendor list, and the 2026 Mibo Smart and Samsung SmartThings announcements do not mention Matter. Intelbras is not a Matter path today. However, Mibo Smart is listed as Works with SmartThings (cameras, locks, lighting, outlets, switches; Samsung–Intelbras partnership, March 2026), so a SmartThings connector gets some Intelbras devices through the cloud. Recommended priorities: (a) Presence: poll the Twibi goform online_list every 15-30 s, or run a minimal TR-069 ACS for Twibi Force. The fallback is ARP/ICMP scanning or DHCP listening from the server, which needs host networking on Umbrel. (b) Sensors and alarm: run a ControlHome-owned Zigbee coordinator with Zigbee2MQTT over MQTT, which is fully local. It is verified for Mibo MSM 1001; Izy (Tuya-made) sensors need per-device testing, and Izy Zigbee locks are reported unsupported in Zigbee2MQTT. The cloud fallback is Tuya: re-pair from the Izy app into Smart Life, then use the Tuya Device Sharing SDK flow or a Tuya IoT project with OpenAPI and the Pulsar message service. (c) Gate and doors: the most reliable local path is a dry-contact relay (ESPHome or Shelly) wired in parallel to the gate controller push-button terminals, plus a reed sensor for state. IP intercoms and access controllers can use their documented HTTP door-release APIs. (d) Tuya Wi-Fi devices: local Tuya protocol on TCP 6668 with protocol versions 3.1-3.5. The .NET option TuyaNet is GPL-3, supports only 3.1/3.3 and has not been updated since 2024. Prefer porting tinytuya (MIT, active) or running it as a sidecar. Caveats: the web-search budget for this run ran out near the end. Still unverified: the exact cloud platform behind Mibo Smart and the MCP 1001 gate actuator, whether the IGD 110 is Tuya, the Izy sensor Zigbee fingerprints, the internal JSON API of the Bifrost web UI, and whether the XPE 3200 HTTP relay works on real hardware.

### Wi-Fi mesh: first-generation Twibi (Tenda Nova MW OEM) (easy)
- Models: Twibi Giga+, Twibi Fast, Twibi Giga (original; web UI availability depends on firmware)
- Path: Local HTTP JSON API used by the router web UI, at the primary node IP (Giga+ default 192.168.5.1). Login: POST http://<node>/goform/set with JSON {login:{pwd:<MD5 of admin password>, timestamp:<ms>}}. Firmware 1.1.11 and later returns a MESH_user session cookie that must be sent back. Read: GET /goform/get?module_id=node_info,online_list,wan_statistic. Other modules: wan_info, lan_info, wifi, guest_info, upnp_info, static_ip, tr069_info, getversion, net_link_status. Writes through /goform/set cover node LED, reboot, guest network and UPnP. ControlHome: implement an IPresenceProvider in .NET with HttpClient that polls every 15-30 s. Match configured phone MACs and debounce with a 3-5 min consider-home window. Fully local, no cloud. Intelbras' Fast firmware 1.1.10 release notes also list TR-069, so the ACS approach from the Twibi Force entry may also apply. The Twibi app (Wi-Fi Control Home) speaks a separate binary protocol on TCP 9000, which community reverse-engineering has not fully decoded for client lists; do not depend on it.

### Wi-Fi mesh/routers on Intelbras Bifrost firmware (Twibi Force family and Wi-Force/RX routers) (moderate)

Source: https://backend.intelbras.com/sites/default/files/2021-10/Manual%20do%20Usuario%20-%20IGD%20110.pdf
- Tuya Device Sharing flow, option A1: Home Assistant's Tuya integration authenticates with an HA-issued client (TUYA_CLIENT_ID 'HA_3y9q4ak7g4ephrvke', TUYA_SCHEMA 'haauthorize'). A .NET reimplementation, or a sidecar for a non-HA product, would have to impersonate HA's client registration, which is not a sanctioned path. The tuya-device-sharing-sdk README does not document how to get your own client ID. The legitimate route for ControlHome's cloud access is option A2, its own Tuya IoT project (OpenAPI plus Pulsar). The SDK itself is MIT, at 0.2.15, and provides SharingMQ and get_device_stream_allocate. Sources: https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/tuya/const.py , https://github.com/tuya/tuya-device-sharing-sdk , https://www.home-assistant.io/integrations/tuya/
- TuyaNet: GPL-3.0 and protocols 3.1/3.3 only are confirmed. The last commit that touched code was Nov 2022; the only 2024 commit (2024-02-20) changed FUNDING.yml. It is effectively unmaintained since 2022, not 2024. tinytuya is confirmed as MIT, protocols 3.1-3.5, with cid/parent gateway sub-device support, discovery on UDP 6666/6667/7000 and TCP 6668, and active releases (v1.20.0 on 2026-07-06). Sources: https://api.github.com/repos/ClusterM/tuyanet/commits?per_page=3 , https://github.com/ClusterM/tuyanet , https://github.com/jasonacox/tinytuya , https://api.github.com/repos/jasonacox/tinytuya/releases?per_page=3
- SmartThings 'token lifetime constraints' is more serious than stated. Personal Access Tokens created after 30 Dec 2024 are valid for only 24 hours, and SmartThings recommends a Service Integration (an OAuth app with refresh tokens) for ongoing access. ControlHome's SmartThings connector must implement OAuth with refresh tokens; a pasted PAT will not work long-term. Source: https://developer.smartthings.com/docs/getting-started/authorization-and-permissions
- ANM 24 NET: the 'local TCP 9009 to the panel' claim is unproven for this model. andregoncalvespires/intelbras_alarm lists ANM 24 Net as NOT validated on real hardware. guardian-api-intelbras lists ANM 24 NET/G2 only as 'V1 Cloud / IP Receiver', with V1 at amt.intelbras.com.br:9015, and not as V2/direct 9009. DanielUlisses/homeassistant_an24net targets 'AN-24 Net' (possibly a different model) through the Intelbras cloud (amt.intelbras.com.br:9009) or a local proxy, and shows no license. Sources: https://github.com/andregoncalvespires/intelbras_alarm , https://github.com/bobaoapae/guardian-api-intelbras , https://github.com/DanielUlisses/homeassistant_an24net
- Allo line: confirmed. A forum post of 17 Feb 2026 reports the wT7 Plus has ports 80, 443, 6987 and 34567 open, 554 closed, no ONVIF WS-Discovery response, and no RTSP. Intelbras's 'app-only' answer is reported second-hand. XR1 is confirmed from its manual: 433.92 MHz, C/NA/NF outputs, a fixed 500 ms pulse, and it works 'exclusivamente com os modelos Allo w3/w3+ e Allo w5/w5+'. Sources: https://forum.intelbras.com.br/viewtopic.php?f=395&start=60&t=66083 , https://backend.intelbras.com/sites/default/files/2021-02/Manual_XR1_01-21_site.pdf
- Matter: confirmed, with one gap. I scanned the CSA DCL vendor list up to character 200,000 of 202,193. It contains Tuya (VID 4701) and 'MiBoxer' (VID 5555, unrelated to Mibo) but no Intelbras. The CSA certified-products search for 'intelbras' returns 'No Entries Found', so Intelbras has no Matter or Zigbee certification under its own name. Neither 2026 article (TechTudo, June; Mundo Conectado, 15 Mar 2026) mentions Matter or Thread. Sources: https://on.dcl.csa-iot.org/dcl/vendorinfo/vendors?pagination.limit=1000 , https://csa-iot.org/csa-iot_products/?p_keywords=intelbras , https://www.techtudo.com.br/noticias/2026/06/intelbras-conecta-casa-com-solucoes-plug-and-play-e-inteligencia-artificial-embarcada.ghtml , https://www.mundoconectado.com.br/samsung/samsung-intelbras-parceria-casa-inteligente/

### Missed options
- Home Assistant as a bridge sidecar, the largest strategic omission. Many of the recommended reference implementations already run inside Home Assistant: rroller/dahua, tuya-local, the official Tuya integration (whose sanctioned HA client ID ControlHome cannot reuse), chiconws Twibi, intelbras_alarm, Matter Server and SmartThings. ControlHome could ship an optional 'HomeAssistantAdapter' that reads and writes entities over HA's WebSocket API, instead of porting each protocol to .NET first, and then replace adapters with native .NET code one at a time. This also removes the Tuya client-ID problem. Sources: https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/tuya/const.py , https://github.com/rroller/dahua
- Dahua/Intelbras event streams without polling. (1) eventManager.cgi?action=attach&codes=[...] is a multipart long-lived event stream (motion, AccessControl, door status), documented in Intelbras' HTTP API V3.35 and in the Dahua access-control instruction (snapManager.cgi?action=attachFileProc with Events=[AccessControl]). (2) The SS 3530 MF FACE 'Serviço de eventos' setting makes the controller push events to an IP, port and path that you configure. ControlHome can expose that HTTP endpoint on the LAN. Source: https://files.dahua.support/Solutions/Access%20Control%20Solution/Integration/DAHUA%20ACCESS%20CONTROL%20PRODUCTS%20INTEGRATION%20INSTRUCTION%20Ver1.0.pdf
- Doorbell and intercom events over SIP for the XPE IP line. The XPE 3200 has 2 SIP accounts and supports point-to-point IP calls, so a local SIP endpoint (an Asterisk/FreePBX sidecar or a small SIP UA) would turn a doorbell press into an incoming-call event, and DTMF can trigger the relay. The XPE 1001/1013 manual also documents 'Envio de logs de acesso em tempo real para servidor Syslog'. A ControlHome syslog listener could therefore receive access events; whether the XPE 3200 has the same feature is UNVERIFIED. Source: https://backend.intelbras.com/sites/default/files/2026-03/Ficha%20t%C3%A9cnica%20-%20XPE%203200%20IP%20Face.pdf
- Plain ONVIF/RTSP for Intelbras VIP cameras and NVRs, using a go2rtc sidecar for WebRTC/MSE in the Vue dashboard plus snapshot.cgi for thumbnails. This path works without any Dahua-specific integration and is the most robust video path. The XPE 3200 publishes RTSP at rtsp://IP/live/ch00_1. Source: https://backend.intelbras.com/sites/default/files/2026-03/Ficha%20t%C3%A9cnica%20-%20XPE%203200%20IP%20Face.pdf
- Original Twibi Giga, which has no web UI: the local Tenda MW6 app protocol is its only local path. kamiljaworski88/tenda_mw6_ha claims client list, online state, signal and rates without cloud, but it is a one-commit project. It could be wrapped as an experimental presence provider. Source: https://github.com/kamiljaworski88/tenda_mw6_ha
- Intelbras Remotize. The Twibi Force AX and Plug Giga datasheets say 'Compatível com plataforma Remotize', and Remotize appears in the TR-098 control parameters. If the owner already uses Remotize, its TR-069 or cloud role conflicts with a ControlHome ACS. A Remotize public API is UNVERIFIED (the site returned only a title). Sources: https://backend.intelbras.com/sites/default/files/2024-06/guia-de-instalacao-twibi-force-plug-giga-pt.pdf , https://manual-bifrost.intelbras.com.br/tr069/index_tr098.html
- Matter as a cross-vendor path. Intelbras is absent from the DCL, but the Tuya VID 4701 is present, so Tuya-ODM products could in principle be certified under Tuya's VID. Check each Intelbras SKU's packaging and QR code rather than relying on the vendor list. Separately, a ControlHome Matter controller (Matter Server or matter.js sidecar) is still worthwhile for LG, Samsung and other vendors. A SmartThings hub can also act as the Matter controller with ControlHome reading it through the SmartThings API. Source: https://on.dcl.csa-iot.org/dcl/vendorinfo/vendors?pagination.limit=1000
- Experimental 433.92 MHz listening for Allo XR1. An RTL-SDR running rtl_433, or an ESPHome CC1101 receiver, could detect when the Allo indoor unit commands the XR1 relay and log it as a 'door opened via intercom' event. The XR1 radio protocol is undocumented (fixed versus rolling code is UNVERIFIED). Use it for receive-only events and never replay. Source: https://backend.intelbras.com/sites/default/files/2021-02/Manual_XR1_01-21_site.pdf
- Allo wT7 Plus exposes TCP 34567, the port used by the Xiongmai 'DVRIP/NETSurveillance' protocol, which suggests an XM-based firmware. Open-source DVRIP clients exist, but the forum author reports the port did not respond to standard tools. Treat this as research only, not a plan item. Source: https://forum.intelbras.com.br/viewtopic.php?f=395&start=60&t=66083
- Shelly Gen2/Gen3 outbound WebSocket and ESPHome native API as push transports for the relay and reed retrofits. Both deliver gate open/closed state changes without polling and without an MQTT broker, if the plan wants to avoid Mosquitto for simple installs. This is an architecture option; no Intelbras source applies.
- Tuya Zigbee generic converters. Many Tuya-made door, motion and siren devices report standard IAS Zone (TS0203/TS0202-style) and work in Z2M through generic or 'TS0601 _TZE...' converters. The Izy devices' Zigbee interview data (modelID and manufacturerName) is the single fact that decides their Z2M feasibility, so the plan should have the owner capture one interview before committing. Source: https://github.com/Koenkk/zigbee2mqtt/issues/31967

### Final recommendation per line
- **Wi-Fi mesh: first-generation Twibi (Giga+, Fast)** (moderate (downgraded from easy: one 0-star reference implementation, firmware coverage inferred from fixtures only)): Implement an ITwibiGoformPresenceProvider in .NET based on the verified chiconws code. Use GET /goform/get?module_id=online_list,node_info. Log in with POST /goform/set {login:{pwd:md5,timestamp}}, and support both legacy auth and MESH_user cookie auth (fw>=1.1.11). Match online_list dev_mac against registered phone MACs, use sn to map the client to a mesh node (coarse room), and debounce for 3-5 minutes. Mark the provider 'community/undocumented'. Have the owner confirm their model and firmware by opening the node IP in a browser before committing. Do not plan on TR-069 for this line until it is proven. Sources: https://raw.githubusercontent.com/chiconws/intelbras_twibi_router/main/custom_components/intelbras_twibi_router/api/connection.py , https://raw.githubusercontent.com/chiconws/intelbras_twibi_router/main/custom_components/intelbras_twibi_router/api/models.py
- **Wi-Fi mesh: original Twibi Giga (no web UI)** (hard): Do not use goform; Intelbras says this model has no web management interface. Use the router-independent presence fallback (ARP/ICMP plus DHCP sniffing). Optionally prototype the Tenda MW6 local app protocol based on kamiljaworski88/tenda_mw6_ha as an experimental provider. Sources: https://backend.intelbras.com/sites/default/files/2020-06/User-guide-TWIBI-GIGA-02.20.pdf , https://github.com/kamiljaworski88/tenda_mw6_ha
- **Wi-Fi mesh/routers on Bifrost (Twibi Force family, W5/W6 Wi-Force)** (moderate): Primary path: run a GenieACS sidecar, or a minimal CWMP endpoint, and poll InternetGatewayDevice.LANDevice.1.Hosts.Host.* (MACAddress, Active, HostName, IPAddress, SignalLevel). Require firmware at or above the releases with the TR-069 fixes (W5-1200F 1.33.19 or later). Check that Remotize or an ISP is not already the configured ACS. Secondary path: test the remote-log feature (UDP 514) for join events. Do not assume the RX 1500/3000 run Bifrost or support HNAP until the owner confirms the hardware. Sources: https://manual-bifrost.intelbras.com.br/tr069/tr-098/ConfigConectados.html , https://manual-bifrost.intelbras.com.br/ChangeLogW5_1200F.html , https://backend.intelbras.com/sites/default/files/2023-05/guia-de-instalacao-twibi-force-ax-pt.pdf
- **Legacy routers (ACtion RF/RG 1200) and router-independent presence fallback** (moderate): Build this generic provider first, because it serves every router: an ARP-table read plus a periodic ARP/ICMP sweep, plus a passive DHCP listener, combined with a consider-home timeout. On Umbrel it needs network_mode: host and NET_RAW. Make it opt-in, since it weakens container isolation. Optionally add a phone-side 'arrived home' webhook on the LAN. Source: https://www.home-assistant.io/getting-started/presence-detection/
- **Gate automation (IGD 110, MCP 1001, Strat ST100)** (easy via relay retrofit; hard via the vendor devices): Make the owner-installed dry-contact relay the supported path: a Shelly Gen2/Gen3 or ESPHome relay wired in parallel on the botoeira terminals, plus a reed switch for state. Use 300-500 ms pulses, a UI confirmation step, and an audit log. Treat IGD 110 as Tuya: its EZ/AP pairing and Izy app pattern are strong evidence, though the category is unverified. Integrate it through tinytuya-style local protocol, or through ControlHome's own Tuya IoT cloud project, only after the owner re-pairs it into Smart Life. Do not plan on SmartThings for MCP 1001: the store page lists Alexa only, and the SmartThings partner listing has no gate or garage category. Sources: https://backend.intelbras.com/sites/default/files/2021-10/Manual%20do%20Usuario%20-%20IGD%20110.pdf , https://loja.intelbras.com.br/acionador-portao-wifi-mcp1001-branco-intelbras/p , https://partners.smartthings.com/partners/mibo-smart
- **Consumer video intercoms (Allo w3/w5/wT7, Allo Box, XR1, IV 7000/7010)** (hard (software); moderate (hardware retrofit)): Do not plan a software integration; the line is confirmed closed and app-only. Use hardware retrofits: an optocoupler input on the bell or chime for press events, and an owner relay in parallel with the lock or gate button. Add a separate ONVIF/RTSP camera for dashboard video. Optionally use a receive-only 433.92 MHz listener (rtl_433) to detect XR1 activations as events. Sources: https://forum.intelbras.com.br/viewtopic.php?f=395&start=60&t=66083 , https://backend.intelbras.com/sites/default/files/2021-02/Manual_XR1_01-21_site.pdf
- **Dahua-OEM cameras, NVRs and SS-series access controllers** (easy): Build a native .NET Dahua CGI adapter with digest auth. Use accessControl.cgi?action=openDoor&channel=1 and getDoorStatus for door control, eventManager.cgi?action=attach for event streams, snapshot.cgi for thumbnails, and RTSP through go2rtc for live view. Also accept the SS controller's pushed events through a 'Serviço de eventos' HTTP endpoint. Treat rroller/dahua as a design reference only, since its README does not claim Intelbras support. Use a dedicated low-privilege device user and back off on 401/403 responses to avoid lockouts. Sources: https://files.dahua.support/Solutions/Access%20Control%20Solution/Integration/DAHUA%20ACCESS%20CONTROL%20PRODUCTS%20INTEGRATION%20INSTRUCTION%20Ver1.0.pdf , https://github.com/rroller/dahua
- **XPE 3200 IP family (IP video door phone)** (moderate (downgraded from easy: the URL is documented only second-hand and was tested only against a mock)): Implement the HTTP relay trigger (GET /fcgi/do?action=OpenDoor&UserName&Password&DoorNum=1) behind a feature flag. It must pass a real-hardware test with the owner before it is marked supported; the DoorNum value and whether the feature must first be enabled on the device both need checking. Use RTSP at rtsp://IP/live/ch00_1 for video. Evaluate SIP registration to a local SIP endpoint for doorbell-press events, and syslog for access logs. Sources: https://github.com/Rodrigohel/dashboard_geral/pull/95 , https://backend.intelbras.com/sites/default/files/2026-03/Ficha%20t%C3%A9cnica%20-%20XPE%203200%20IP%20Face.pdf , https://www.comfortclick.com/Support/ExampleDetails/Akuvox
- **Izy alarm and Zigbee sensors and locks (ICA 1001, ISA/ISM/ISI 1001, IDF/IDG 620, IFR/FR locks)** (moderate-to-hard (cloud is moderate; fully local is unproven)): Keep these on the Izy/Tuya hub, and integrate through ControlHome's own Tuya IoT cloud project: OpenAPI plus Pulsar, after re-pairing into Smart Life. Do not reimplement HA's Device Sharing client, because it uses HA's issued client ID. As a local step, try tinytuya-style gateway sub-device polling using cid. Before planning a Zigbee2MQTT migration, capture one Izy sensor's Zigbee interview data; Intelbras says ISA 1001 works only with Izy hubs, and Z2M support is unverified. Keep the locks on the Tuya hub: Z2M shows them as unsupported, and the tuya-local sub-device request was closed as not planned. Sources: https://backend.intelbras.com/sites/default/files/2021-02/datasheet-ISA-1001.pdf , https://homeassistantbrasil.com.br/t/hub-de-automacao-inteligente-izy-smart-ica-1001-intelbras/6934 , https://github.com/make-all/tuya-local/issues/6040 , https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/tuya/const.py
- **Mibo Smart line (MCA 1001 hub, MSM 1001, MTU 1001, MFR locks, iM cameras)** (easy for MSM 1001; moderate for the SmartThings cloud path; unknown for the other devices): MSM 1001: re-pair it to ControlHome's Zigbee2MQTT (2.11.0 or later) and consume it over MQTT; this is verified. Other Mibo Zigbee devices (MTU 1001 and others): require an interview capture per device before committing. Cameras, locks, lighting, outlets and switches: use a SmartThings connector with OAuth and refresh tokens (PATs now expire after 24 hours) and polling, because the LAN app has no public webhook. The cloud backend behind Mibo Smart itself is UNVERIFIED. Sources: https://github.com/Koenkk/zigbee2mqtt/releases/tag/2.11.0 , https://loja.intelbras.com.br/sensor-temperatura-umidade-mtu-1001/p , https://partners.smartthings.com/partners/mibo-smart , https://developer.smartthings.com/docs/getting-started/authorization-and-permissions
- **Izy Wi-Fi devices (plugs with metering, switches, lamps, IR, cameras)** (moderate): Port the tinytuya protocol code to .NET (MIT, protocols 3.1-3.5, active through v1.20.0 in Jul 2026), or run it as a sidecar. Do not use TuyaNet: it is GPL-3, supports only 3.1/3.3, and its code has been unchanged since Nov 2022. Get the local_key once through ControlHome's own Tuya IoT project, and maintain per-product DP maps. Use the Tuya cloud adapter for cameras. Because the Izy and Tuya apps reportedly cannot control the same device at once, the owner must accept losing the Izy app for migrated devices. Sources: https://github.com/jasonacox/tinytuya , https://api.github.com/repos/ClusterM/tuyanet/commits?per_page=3 , https://homeassistantbrasil.com.br/t/hub-de-automacao-inteligente-izy-smart-ica-1001-intelbras/6934
- **Matter across Intelbras lines** (not-feasible (for Intelbras today)): There is no Intelbras Matter path. Intelbras has no DCL vendor entry and no CSA-certified products, and the 2026 announcements do not mention Matter. Still build a generic Matter controller adapter (Matter Server or matter.js sidecar) in a later phase for other vendors such as LG and Samsung. Re-check Intelbras SKUs individually for Tuya-VID Matter certification. Sources: https://on.dcl.csa-iot.org/dcl/vendorinfo/vendors?pagination.limit=1000 , https://csa-iot.org/csa-iot_products/?p_keywords=intelbras
- **Non-AMT monitored panel ANM 24 NET (only if the owner has one)** (hard (downgraded from moderate: untested on real hardware, and the local protocol support is unclear)): Defer until the owner confirms the exact model. If confirmed, start with the IP-receiver mode (the panel pushes events to ControlHome, accepted only from the panel's IP) for monitoring. Treat arming and disarming as a later, PIN-gated, audited feature, after verifying whether the panel supports direct local port 9009 at all; current sources show only V1 cloud and the IP receiver for this model. Sources: https://github.com/bobaoapae/guardian-api-intelbras , https://github.com/andregoncalvespires/intelbras_alarm
